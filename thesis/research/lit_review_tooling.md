# Citation-graph literature review tooling for auto-research (Claude Code)

Context: current lit review relies on keyword web search and misses papers. Goal: add
citation-graph discovery (snowballing) usable from scripts/agents on a low budget.

## 1. APIs

| API | Free tier / rate limit | Relevant endpoints | Notes |
|---|---|---|---|
| **Semantic Scholar Graph API** | No key: shared pool, ~1000 req/s *across all* unauthenticated users (heavily throttled in practice, effectively low burst per IP). With free API key (request at https://www.semanticscholar.org/product/api, few days turnaround): 1 req/s guaranteed per key, occasionally raised on request. | `/graph/v1/paper/{id}`, `/paper/{id}/citations`, `/paper/{id}/references`, `/recommendations/v1/papers/forpaper/{id}`, bulk search `/graph/v1/paper/search/bulk`, batch details `/graph/v1/paper/batch` | Best single source for citation graph. Use batch/bulk endpoints to conserve the 1 req/s budget. Returns abstracts, tldr, fieldsOfStudy, up to 1000 citations/refs per call. Docs: https://api.semanticscholar.org/api-docs/ |
| **OpenAlex** | Free, no key required; "polite pool" (add `mailto=` param) gives higher priority, ~10 req/s, 100k req/day documented. | `/works/{id}`, `referenced_works`, `related_works`, cited-by via `filter=cites:{id}`, full-text/abstract inverted index | Larger coverage than S2 (successor to Microsoft Academic Graph), good for backward+forward citation edges and as a dedupe/ID-resolution layer (has DOI/arXiv/PMID mappings). https://openalex.org |
| **arXiv API** | Free, no key; rate-limited informally (~1 req/3s recommended by arXiv). | Atom API `export.arxiv.org/api/query`, plus arXiv listing/OAI-PMH | Good for metadata + LaTeX source retrieval (source tarballs at `arxiv.org/e-print/{id}`) for deep-read step. No citation graph. |
| **Crossref REST API** | Free, no key; "polite pool" via `mailto=` param, generous (effectively unlimited for reasonable use). | `/works/{doi}`, `is-referenced-by-count`, reference lists (when publisher supplies them) | Useful for DOI resolution and reference lists of non-arXiv (journal/conference) papers; citation data is sparser/less consistent than S2/OpenAlex. |
| **alphaXiv** | No public documented API/key program found as of 2026-09; site offers paper discussion overlay on arXiv. | — | Not usable programmatically; skip for pipeline, optionally web-fetch for community discussion signal only. |
| **Papers with Code (successor)** | PwC dataset/API was archived (Meta shut down active development ~2023-2024); data dump still downloadable as static JSON on their site, no live API. | — | Skip; not a live source. |
| **Connected Papers** | No public API; web app only (graph visualization). | — | Manual/inspection use only, not scriptable. |
| **ResearchRabbit** | No public API; free web app (unlimited personal use) with citation-graph exploration ("similar work", "earlier/later work"). | — | Good manual cross-check tool, not automatable from agents. |
| **Litmaps** | No free public API; paid API tiers exist for enterprise/institutional accounts, not documented as self-serve. | — | Skip for a low-budget pipeline. |

**Practical takeaway:** build the snowball graph from **Semantic Scholar (with a free API key) + OpenAlex** (cross-validate/fill gaps), resolve/enrich with **arXiv API** (for source retrieval) and **Crossref** (for non-arXiv DOIs). Skip alphaXiv / PwC / Connected Papers / ResearchRabbit / Litmaps for automation — no usable free APIs.

**Assessment:** none of these MCP servers are "mature" in the sense of official/Anthropic-maintained — all are small community projects. For reliability on a low budget, prefer **calling the Semantic Scholar / OpenAlex / arXiv REST APIs directly from a Python script** (full control over batching, caching, backoff) over depending on a thin, possibly-unmaintained MCP wrapper. Use `paper-search-mcp` opportunistically inside interactive Claude Code sessions for exploratory multi-source search, but keep the core snowball/rank/fetch pipeline as your own script for reproducibility.

## 3. Agentic literature-review systems

- **PaperQA2 (FutureHouse)** — https://github.com/future-house/paper-qa. RAG over PDFs/full text with agentic tool use (search, gather evidence, cite); SOTA on RAG-QA Arena science benchmark; now used inside FutureHouse's hosted platform (Crow/Owl/Falcon tiers) and pulls OpenAlex metadata. Strongest at *answering a specific question with grounded citations from full text*, less strong as a discovery/snowballing tool by itself.
- **Elicit** (elicit.com) — commercial, strong at systematic-review-style structured extraction across many papers (tables of methods/results); free tier limited; no cheap programmatic API for bulk agent use.
- **Undermind** (undermind.ai) — deep semantic search that iteratively refines a "true" set of relevant papers, marketed as more thorough than keyword search for literature discovery; commercial, limited free queries.
- **OpenScholar (Ai2 / UW)** — https://openscholar.allen.ai — open-weights retrieval+LM pipeline, benchmarked on ScholarQABench (2,967 queries, multi-domain); outperformed PaperQA2 and GPT-4o on correctness for multi-paper synthesis in the original paper. Ai2 has since folded this into **Asta** (Ai2's broader "Scholar" agent suite, incl. Paper Finder) — Asta/Ai2 Paper Finder is positioned as a more transparent alternative to closed deep-search tools (see Aaron Tay's 2026-02 comparison of Ai2 Paper Finder vs. PaperQA2).
- **STORM (Stanford)** — outline-driven, multi-perspective question-asking agent for writing Wikipedia-style survey articles from web sources; good architecture reference for "structured survey generation" but not citation-graph-based itself.
- **GPT-Researcher** — general web-research agent (not citation-graph aware), useful as an orchestration pattern but not literature-specific.
- **AI Scientist (Sakana AI)** and **Agent Laboratory** — full closed-loop "idea → experiment → paper" agents; their literature-review sub-step is typically simple keyword/API search (Semantic Scholar), not sophisticated snowballing — useful as prior art for how much lit-review effort is "enough" before experiments, not as a component to copy directly.
- **2025-2026 benchmarks**: ScholarQABench (OpenScholar paper) and RAG-QA Arena (PaperQA2) are the two concrete published benchmarks comparing these systems; the Aaron Tay substack/blogspot post (2026-02, "Ai2 Paper Finder and FutureHouse PaperQA2: More transparent Deep Search for Scholars?") is a useful informal 2026 comparison of the two leading "deep search" agents from a librarian's perspective.

**Takeaway:** none of these are cheaply reusable as a drop-in citation-graph snowballer for a solo low-budget project — they're either commercial (Elicit, Undermind), require hosting a full RAG stack (PaperQA2, OpenScholar), or are general-purpose research agents without citation-graph specificity (STORM, GPT-Researcher, AI Scientist, Agent Laboratory). Best move: borrow the *architecture idea* (iterative retrieve → triage → deep-read → synthesize, as in PaperQA2/OpenScholar) but implement the graph traversal yourself directly against Semantic Scholar/OpenAlex, since that part is cheap and you need full control over budget.

## 4. Recommended pipeline (Claude Code, low budget)

1. **Seed set** — 5-15 hand-picked seed papers (arXiv IDs / DOIs) directly relevant to the project (indexed attention, KD, memory/composition, etc.), stored in a small YAML/JSON in `dev_notes/` or `thesis/research/`.
2. **Snowball, depth 2** — script (`learn/litreview/snowball.py` or similar) calls Semantic Scholar `/paper/{id}/citations` and `/references` (backward+forward) for each seed, then repeats one more hop on the new set (depth 2). Cross-check/fill missing papers via OpenAlex `referenced_works`/`related_works` for anything S2 doesn't resolve (e.g. non-CS venues). Cache every API response to disk (JSON per paper ID) so re-runs are free.
3. **Dedupe + rank** — dedupe by DOI/arXiv ID/normalized title. Rank candidates by a cheap signal first (citation count, publication venue, recency, textual overlap of title/abstract with seed set keywords via simple embedding — e.g. local `sentence-transformers` or one batched Haiku call over abstracts only), then use a single batched **Claude Haiku** call (all candidate titles+abstracts in one prompt, structured JSON output: relevant/maybe/no + one-line reason) to triage into a shortlist of ~20-40 papers. This is the main cost-control step: never send full text to an LLM at this stage, only titles/abstracts.
4. **Deep read top-N** — for the shortlisted papers, fetch arXiv LaTeX source (`arxiv.org/e-print/{id}`) when available (much cheaper/cleaner tokens than PDF-to-text), otherwise fall back to abstract+Semantic Scholar TLDR only for non-arXiv papers you can't get full text for cheaply. Feed only the sections needed (method, results) to a Sonnet-tier agent for structured note extraction — chunk large LaTeX files and summarize incrementally rather than dumping the whole source into context.
5. **Structured notes + bibtex** — agent writes one short structured note per deep-read paper (problem, method, key result, relation to our work) into `dev_notes/lit/` and appends a bibtex entry (fetched from Crossref/S2 `externalIds`/arXiv metadata, not hand-typed) to `thesis/paper/references.bib`. Keep the snowball graph (edges + all candidate metadata, not just the shortlisted ones) cached so future passes only need to fetch *new* citing/cited papers, not redo the whole graph.

**Cost-saving tactics:** cache all API responses; batch Semantic Scholar calls (`/paper/batch`) instead of per-paper requests; do triage on abstracts only with Haiku (cheapest tier) before any Sonnet/Opus full-text reading; prefer arXiv LaTeX source over PDF text extraction; only deep-read the final N (e.g. 15-25) papers, not the full snowball set (which at depth 2 from ~10 seeds can easily be 500+ candidates).
