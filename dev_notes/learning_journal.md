## 2026-09-03/04 — Grid'5000 besteffort: why did it fail, and are we in it?
- Question: (asked twice, related) First, after a normal GPU reservation was rejected on `abacus27` despite it showing `busy_free_besteffort`: "pourquoi le besteffort n'a pas fonctionné, que dit la doc là-dessus ?" Later, after realizing the same thing kept happening: "pouvons-nous nous-mêmes être préemptés, sommes-nous en besteffort, dans quels cas ?"
- Core explanation: Two distinct mechanisms were involved, and untangling them was the actual learning moment. (1) Besteffort preemption is real and documented (Grid'5000's `Advanced_OAR` wiki page: a normal job can and does kill a besteffort job holding a resource it needs) — but that's not what was happening here. (2) The real cause, found by testing `-q abaca` directly: the `wide` group has **no priority GPU allocation at Rennes at all** — every GPU reservation for this project can only ever be submitted `-t besteffort`, meaning it's *us* who are always the preemptable one, never the preemptor, on Rennes GPUs specifically. This is a project/group access-control fact (who gets priority queue access), not a scheduling race or a besteffort mechanism failure — an earlier "race condition" theory was an incomplete diagnosis before this was found. Practical consequence: any GPU job on Rennes for this project must assume it can die at any moment with no warning, and should save progress incrementally (to home/Group Storage, not `/tmp`) rather than assuming a walltime-length window.
- Status: confirmed (root-caused via direct testing, not just documentation reading)
- Related: grid5000-storage-persistence

## 2026-09-04 — How should hyperparameters be tuned as model size scales up?
- Question: Before moving from the current small student (~10-41M params) toward larger tiers (50M, 150M, ...), should hyperparameter tuning (mainly learning rate) happen fresh at each tier, or is there a smarter way to avoid re-tuning every time, given tuning experiments are expected to get much more expensive at larger scale? Concern: tuning only at small scale and reusing the same raw values at large scale risks getting "trapped" in values that were only optimal for the small model.
- Core explanation: This is a well-known failure mode under standard neural net parametrization — the optimal learning rate systematically shifts with model width, so values tuned small do NOT transfer as-is to a wider model. The established fix is **muP** (Maximal Update Parametrization; Yang et al., *Tensor Programs V*): a specific init-variance and per-layer learning-rate scaling rule (as a function of width) under which the *optimal* LR becomes stable across width — tune cheaply on a narrow model, reuse the same LR unchanged on the wide target model. Implemented a "muP-lite" version (init + LR scaling; skipped the attention-scaling refinement) in `train_sft.py`, and ran a real width-transfer test on the actual `reasoning` data (4 learning rates × 3 configs: narrow+muP, wide+muP, wide-without-muP): at the most aggressive LR tested, the no-muP wide model's loss drifted noticeably worse (6.035 vs a narrow-model baseline of 5.809) while the muP wide model tracked the narrow baseline almost exactly (5.811) — a real, if modest, confirming signal specific to this codebase, not just theory.
- Status: confirmed (both the general research answer and a codebase-specific empirical check)
- Related: (none yet)

## 2026-09-04 — Weight tying: what exactly is shared between embedding and lm_head?
- Question: After choosing to keep the embedding and lm_head tied (rather than following muP's canonical untying), what does "shared" actually mean here — what's on the input side, what's on the output side, and why does muP care?
- Core explanation: Both the input embedding and the output projection (lm_head) are matrices of the same shape `(vocab_size, n_embd)`. Input side: a lookup — token id → its row in the matrix, no matmul, just an index. Output side: the final hidden vector (`n_embd`-dim) is matrix-multiplied against the same matrix (transposed) to get one score per vocabulary token. "Weight tying" (a standard, pre-muP technique, Press & Wolf 2016) reuses one matrix for both roles to halve the vocab-sized parameter count. muP's canonical recipe wants to treat these two roles differently — input embedding gets base (unscaled) init/LR since it's just a lookup, not a width-dependent matmul; the output/readout gets near-zero init and its logits divided by `width_mult`, since a matmul's output magnitude does grow with width and muP corrects for that. Those are two different prescriptions for the same physical tensor if tied — hence canonical muP requires untying so each can get its own correct treatment. This project's compromise: keep tying (avoids doubling an already-huge 248k-vocab table relative to a small core), but still apply the logit/width_mult division at the loss — the part of muP's readout treatment that most directly controls training dynamics — while skipping the zero-init/untie. A real, acknowledged deviation from canonical muP, not the full recipe.
- Status: confirmed
- Related: mup-hyperparameter-transfer

## 2026-09-04 — Top-K distillation & dataset vocabulary coverage
- Question: With a ~152k-token vocabulary and a fairly small dataset (200-38k examples for the `reasoning` category), does capturing the Teacher's Top-K=32 logits per token actually give the student useful signal across the vocabulary — or are there vocabulary tokens that simply never appear anywhere in the dataset, meaning no value of K helps for those?
- Core explanation: Top-K and "dataset vocabulary coverage" are two independent questions. Top-K controls, at each token POSITION that occurs in the data, how much of the Teacher's probability mass over the full vocabulary is captured (usually most of it, since LM distributions are typically peaked — a handful of tokens dominate). It says nothing about which vocabulary items appear ACROSS the dataset. A token that never occurs as a target anywhere in the training data gets zero gradient signal touching its embedding/readout row, no matter how large K is — that's a separate, checkable fact: tokenize the full dataset, count distinct token ids seen, compare to vocab_size. This matters more for small/narrow-domain datasets (e.g. math reasoning traces) than for broad general-text corpora, since a narrow domain naturally uses a narrower slice of the vocabulary (many tokens for e.g. rare Unicode scripts, uncommon words, or other languages may just never show up).
- Status: **confirmed** — measured directly on the full `reasoning/train.jsonl` (34,252 examples, 91,256,892 tokens): only **38,308 distinct token ids** appear, out of a **248,077**-token vocabulary (this tokenizer's real size — corrects an earlier repo note that assumed ~151,936, the plain-Qwen3-text figure; this checkpoint's VLM tokenizer is larger). That's **15.44% vocabulary coverage** — 84.56% of the vocabulary never appears anywhere in this dataset and gets zero training signal on its embedding/readout row regardless of Top-K. Confirms the hypothesis: for a narrow-domain dataset (math reasoning traces), most of a large shared vocabulary is simply unused. Whether this matters depends on intended use — irrelevant if the final model only ever sees similarly-scoped inputs, a real gap if broader coverage (other languages, general text, code, etc.) is expected. Not yet checked: coverage of the `general`/`retrieval` categories, or the union across all three.
- Related: distillation-topk-storage-formula, mup-hyperparameter-transfer

## 2026-09-04 — Why the LR "optimized" at small scale broke the next tier
- Question: After running a real hyperparameter sweep (LR/kd_alpha/weight_decay) instead of reusing a hand-picked value, why did the best config found at 40M-core (lr=0.01) give a much WORSE result at 150M-core (1.28 vs. 0.29), when muP is supposed to guarantee the optimal LR doesn't move with scale?
- Core explanation: muP only guarantees LR-optimum invariance with respect to **width** (`n_embd`), at fixed depth. But this project's tier progression changes `n_embd` AND `n_layer` at the same time (4→12→25 layers). Stacking more layers needs a lower LR independent of muP (residual-stream accumulation) — a separate effect not covered by the width-only muP scaling applied here. So the cross-tier "transfer test" was never a pure width test — depth was an unidentified confound the whole time. Counter-intuitive but logical result once understood: `lr=0.003` (used from the start, never verified optimal in isolation) turned out to be a better multi-tier compromise than the value that *was* verified optimal... but only at the narrowest AND shallowest tier.
- Status: confirmed (measured directly: lr=0.003/0.005/0.007/0.01 give a strictly opposite ranking at 40M vs. 150M-core)
- Related: mup-hyperparameter-transfer, model-size-tiers-core-vs-head, depth-mup-fix

## 2026-09-04 — Depth-muP: fixing the depth confound
- Question: Following the discovery that the LR optimized at 40M broke at 150M/500M because of the simultaneous depth change, how do you actually fix that in code, and does it really work?
- Core explanation: The standard fix (Depth-muP / Tensor Programs VI literature) multiplies each residual branch's output (attention and MLP, right before the residual add) by `1/sqrt(n_layer / reference_depth)`. Implemented via forward hooks on each block's `.attn`/`.mlp` submodules (rather than rewriting the whole block's `forward` — more robust to `transformers` version changes). Tested directly: with this fix, the "optimized at 40M" LR (0.01) becomes competitive again at 150M (2.7x better than without it, still a bit behind the old setting) and is outright BETTER than the old setting at 500M (0.32 vs. 0.38) — the fix helps more as the depth ratio grows, consistent with the theory.
- Status: confirmed (empirical result measured at all 3 tiers, neutral effect verified exactly at the reference depth)
- Related: mup-hyperparameter-transfer, transfer-broke-at-150M

## 2026-09-13 — Effective rank / participation ratio: what does it measure, and on what part of a model?
- Question: "le rang effectif c'est sur quelle partie du model que tu l'evalue" — after seeing a participation-ratio number reported for several weight matrices during the n_hops=2 mechanistic diagnostic.
- Core explanation: It's computed on individual weight MATRICES (`nn.Linear.weight`, e.g. `q_proj`/`k_proj`, shape `(d, d)` here), never on an activation or the whole model. A `d x d` matrix has a nominal capacity of `d` independent directions, but can behave as if it only really used a handful of them (most of its singular values ~0, one or two dominating) even though nothing forces that — that's what "collapse" means (see next entry). The participation ratio `(sum(sigma))^2 / sum(sigma^2)` (from the matrix's singular values `sigma_1>=...>=sigma_d>=0`) summarizes this in one number: equals `d` (the max) if all singular values are equal (no collapse), tends to 1 if one singular value dominates everything (near-total collapse to a single direction). Measured 21-29 out of a max of 32 for every projection checked in this diagnostic (`q_proj`, `k_proj`, `v_proj`, `sm_q_proj`, `fuse_proj`) -- no low-rank collapse, these matrices use nearly all their nominal capacity. Important caveat found the same session: this only rules out ONE specific failure mode (lazy low-rank degeneracy) -- it says nothing about whether the mechanism actually WORKS, which turned out to be broken for an unrelated reason (see the self-match entry below).
- Status: confirmed
- Related: weight-collapse-concept, n-hops-composition-plateau

## 2026-09-13 — What is "representation/weight collapse" and how do you actually detect it?
- Question: "c'est quoi un effondrement et comment sais tu qu'il n'y en a pas" -- asked right after the participation-ratio explanation above.
- Core explanation: "Collapse" here means a component's EFFECTIVE behavior is much simpler/more degenerate than its nominal capacity would allow -- e.g. a `32x32` weight matrix that, despite having 32 rows/columns on paper, only actually varies along 2-3 real directions (the rest of its singular-value spectrum near zero), or a set of supposedly-distinct learned vectors (e.g. keys for different tokens) that all end up nearly identical to each other regardless of their input. It's detected by looking at the actual SPREAD of the quantity in question rather than its nominal size: for weights, the singular-value spectrum / participation ratio (previous entry); for a set of vectors meant to be distinct (e.g. this session's test of 200 distinct KB keys), the pairwise cosine similarity among them -- near 1.0 on average would mean collapse (all keys look alike), whereas a moderate value with real spread (measured 0.39 mean, 0.21 std here) means they're still meaningfully different from each other. Both checks came back negative (no collapse) in this session's diagnostic, yet the underlying retrieval mechanism was still shown (by a separate, more direct causal/ranking test) to be broken -- collapse is one specific failure mode among several, ruling it out doesn't mean the mechanism works.
- Status: confirmed
- Related: effective-rank-participation-ratio, n-hops-composition-plateau

## 2026-09-13 — What would it mean if the shared source_bias term "swamped" content, and why check?
- Question: "biais ecrase le contenue meme si c'est pas le cas que cela signifie t'il" -- after reporting that source_bias doesn't dominate content (ratio 0.877).
- Core explanation: In `HierarchicalMemory`, every KB leaf's key is `k_proj(token_embedding + source_bias)`, where `source_bias` (one of two learned rows, "input" vs "KB") is the exact SAME vector added to every single KB key regardless of its actual token content. If that shared additive term had a much larger norm than the token-embedding-driven variation between different keys, then after projection, all KB keys would end up looking nearly identical to each other in the space the attention mechanism actually compares them in -- the same practical effect as "collapse" above, but caused by a different, very concrete and fixable mechanism (one could down-weight or remove the bias term) rather than a vague training pathology. Measured: shared-bias-term norm ~2.90 vs. content-variation norm ~3.31 (ratio 0.88) -- comparable, not swamping, so this specific, easily-actionable explanation is ruled out here. Useful methodologically: this was checked BEFORE assuming a vaguer explanation, since it would have been the simplest and most directly fixable one if true.
- Status: confirmed
- Related: weight-collapse-concept, n-hops-composition-plateau

## 2026-09-13 — How does a token get "injected" into Thinker's recurrent register, and which embedding table?
- Question: "comment injecte tu les embedding dans le model dans les register comment c'est possible de quell embedding s'agit t'il" + "as tu utiliser les embeddding des couches intermediaire dans le ouputstream" -- while explaining the causal-intervention diagnostic (forcing R to a specific value mid-loop).
- Core explanation: In the real forward pass, `Thinker.forward` seeds the register with `R = register_init (learned parameter) + self.embed(query_tokens).mean(...)` -- `self.embed` is a plain `nn.Embedding(vocab_size, d_model)`, a lookup table (token id -> its row, no matmul), the SAME table used to embed the KB's leaf tokens -- not a Teacher's embeddings, not any intermediate-layer activations. "Injecting" a value in the diagnostic script just means reassigning that same tensor mid-loop in a hand-unrolled copy of the forward loop (`R = register_init + self.embed(some_other_token)`, at a chosen iteration `t`) -- possible only because the diagnostic script re-implements the loop explicitly in Python rather than calling the compiled/opaque `forward()`, so any local variable can be overwritten between iterations. Clarified explicitly: no Teacher intermediate-layer embeddings were used anywhere in this diagnostic -- that's a SEPARATE, unimplemented idea (spec §11bis's `thinking` output stream, meant to align an output stream with a Teacher's hidden layer) that this session's work never touched.

## 2026-09-13 — What is the "isolated random-token self-match" test, and a bug found while explaining it
- Question: "c'est quoi cette auto appariement isole de tokens aleatore" -- the last of a batch of clarifying questions about the n_hops=2 mechanistic diagnostic.
- Core explanation: `q_proj` turns an embedding into a "query", `k_proj` turns an embedding into a "key" -- if the matching mechanism works, the query built from token `x` should be MORE similar (cosine) to the key built from that SAME token `x` than to keys built from other tokens `y`. The test embeds several tokens, computes query and key for each, and checks whether the correct (self-) match ranks near the top among all candidates -- deliberately stripped of the register/hierarchy/episode structure, to isolate just the `q_proj`/`k_proj` primitive. The first version of this test requested `torch.randperm(vocab_size)[:300]` where `vocab_size` was actually only 34 (this toy setup's ENTIRE vocabulary: 32 content tokens + 2 markers) -- `randperm(34)` can only return 34 elements, and Python silently returns whatever exists when slicing past a tensor's length rather than raising, so the test was secretly comparing among 34 tokens, not 300, and the reported "chance level = 150, mean rank ~21/300 = above chance" was wrong on both counts. Caught by explaining the test out loud while answering this question (a real instance of the rubber-duck effect) and re-verified in a Python one-liner before touching any conclusion. Corrected result: mean rank ~21.4 out of the true 34 (chance 16.5) -- actually slightly WORSE than chance. This also resolved an apparent contradiction reported earlier the same session (isolated matching allegedly working, in-episode matching allegedly broken) -- both are at-or-below chance once measured correctly; the "tension" was an artifact of this bug, not a real phenomenon.
- Status: confirmed (bug found, fixed, and re-verified same session)
- Related: n-hops-composition-plateau, effective-rank-participation-ratio
