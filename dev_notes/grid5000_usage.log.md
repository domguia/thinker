- Recovered what was recoverable: a compute-appropriate CPU job (`oarsub -l host=1 -q default`, job 4105628, `parasilo-15`, NOT the frontend -- a first attempt to `torch.load` the checkpoint directly on the Rennes frontend to save time was killed with exit 137, presumably an OOM/resource guard on the shared login node; confirms the skill's "never compute on the frontend" rule isn't just about being polite, it can silently kill your own commands) gave the checkpoint's final step (11500) and train-loss history; `eval_val_loss.py` against that checkpoint gave one salvaged data point: `val_loss=0.456, val_ce=0.107, val_kd=0.805` at step 11500 -- close to the earlier completed run's step-13340 result (`val_loss=0.4585, val_ce=0.0985, val_kd=0.8185`), suggesting the KD-term divergence had likely already plateaued well before 11500, but this is inference from a single late point, not the requested curve.

## 2026-09-19/20 (nuit) — Stratégie stockage/transfert pour sites hors Rennes : mesures réelles + recommandation

**Contexte** : tâche déléguée par l'utilisateur via `experiment-manager`, suite au transfert manuel du fichier real-text vers Nancy plus tôt ce soir. Objectif : trancher entre (1) transfert inter-site depuis Rennes/killerdroid, (2) stockage minimal dans le home du site cible, (3) re-téléchargement/reprocessing sur place — avec des mesures, pas des suppositions. Utilisé les réservations déjà actives (pas de nouvel `oarsub`) : Rennes job `4121245`, Nancy `graffiti-3` job `6933303`.

**Mesures** (fichier test 1 Go / 2 Go, `dd`/`rsync`/`curl`, une seule passe chacune — ordre de grandeur, pas un benchmark statistique) :
- `rsync` Rennes home → Nancy home (inter-site, réseau Grid'5000 interne) : **~140-150 MB/s** (1 Go transféré en ~7s de transfert net).
- Disque local `/tmp` sur `graffiti-3` (Nancy), écriture et lecture en O_DIRECT (pas de cache page) : **~380-400 MB/s**, soit ~2.7x plus rapide que le transfert inter-site.
- Home NFS Nancy, lecture locale au site (même site que le compute node) : **~1.1 GB/s** — network intra-site nettement plus rapide qu'inter-site, cohérent avec l'archi Grid'5000 (chaque site a son propre stockage/réseau).
- Téléchargement direct depuis Hugging Face (`gpt2/pytorch_model.bin`, 548 Mo) exécuté **depuis le nœud de calcul Nancy lui-même** (pas le frontend) : **~94 MB/s** réel — accès internet sortant confirmé fonctionnel sur les nœuds de calcul, pas seulement les frontends.

**Recommandation** :
1. **Si la donnée est publique et disponible en ligne (modèle HF, dataset public) : télécharger directement sur le site cible plutôt que relayer via Rennes.** Le débit (~94 MB/s) est comparable au transfert inter-site (~140 MB/s) — pas de gain net à transiter par Rennes — et ça évite (a) de gonfler le home Rennes (déjà proche/au-delà de son quota, cf. l'incident 153GB plus haut dans ce log) et (b) une double reprocessing/synchro. Seule exception : un token HF privé ou un accès restreint uniquement configuré côté Rennes.
2. **Si la donnée n'existe que sur Rennes/killerdroid (checkpoint distillé, cache d'activations, artefact déjà transformé) : transférer via `rsync` inter-site, c'est la seule option — mais viser le strict nécessaire.** À 140 MB/s, un cache de 32 Go prend ~4 min, largement moins cher qu'un recompute complet dans la quasi-totalité des cas concrets de ce projet (le compute est le facteur limitant, pas le réseau).
3. **Ne jamais stocker plus que le strict nécessaire dans le home du site cible** (déjà la doctrine documentée dans `new_site_env_setup.md`/`compute_scheduling.md`, confirmé ici empiriquement) : les sites hors Rennes ont un quota home plus faible, et le disque local `/tmp` du nœud réservé est de toute façon ~2.7x plus rapide que n'importe quel chemin réseau pour l'I/O réel d'entraînement — le home ne doit servir que de point de passage transitoire (staging), jamais de zone de travail active.
4. **Recompute sur place seulement si strictement moins cher que le transfert** : pas rentable pour un artefact déjà produit et de taille modeste (<~50 Go) vu le débit inter-site mesuré ; peut le devenir seulement pour un recompute très rapide (secondes/minutes) sur un dataset qui, lui, est trivialement retéléchargeable (cas 1 ci-dessus, qui domine de toute façon).

**Notes / follow-up** : mesures faites en une seule passe chacune (pas de moyenne sur plusieurs runs), donc ordres de grandeur fiables mais pas des bornes statistiques strictes — suffisant pour trancher entre les 3 stratégies, qui diffèrent d'un facteur >2-3x et non marginalement. Nettoyage fait (fichiers test supprimés sur Rennes/Nancy home et `/tmp` Nancy). Transmis à `experiment-manager` en retour.
